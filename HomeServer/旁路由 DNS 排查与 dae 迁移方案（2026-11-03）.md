## 2. DNS 排查：踩了三次坑才弄清楚

> [!bug] 现象
> Mac 问主路由 `dig x.com @192.168.5.1`，返回的是 mihomo 的 fake-ip（198.18.0.106，TTL 1）。

**错误推断 1**：Mac 拿到的是真实 IP。→ 实测不对。
**错误推断 2**：主路由的上游 DNS 是旁路由。→ 也不对。旁路由自己直接问主路由，拿到的是真实 IP；ShellCrash 里"拦主路由 DNS"那条规则的计数是 0。

**真正的机制**：

1. Mac 的路由表里有一条**克隆出来的主机路由**：`192.168.5.1 → 网关 192.168.5.5`（标志 `UGHWIig`，`Use` 13547，不会过期）。
   - 普通 `netstat -rn` 不显示，要 `netstat -rnal` 才看得到。
   - `W` 表示克隆，`G` + 网关 5.5 说明它是从 **default 路由**克隆的。推测是开机或网络重连时，子网路由还没装上，mDNSResponder 就去问 5.1 了。因为一直有 DNS 查询在用，它就一直没被回收。
   - `traceroute 192.168.5.1` 第一跳是 5.5；Mac 的 ARP 表里根本没有 5.1。
2. 发往 5.1:53 的包到了旁路由，被 `shellcrash_dns` 规则（`-s 192.168.5.0/24 udp dport 53 → REDIRECT 1053`）截下来，交给 mihomo 回答。
3. 回包时 conntrack 把源地址改回 5.1，Mac 以为是主路由回的。
   - 验证：Mac 问"5.1"3 次，这条规则的计数正好 +3。
4. 旁路由其实一直在给 Mac 发 ICMP 重定向（"5.1 你直接找它"），Mac 一共收到 15267 次，但 macOS 默认 `drop_redirect=1`，全部丢掉了。

> [!important] 结论
> **Mac 能分流是碰巧的。** 那条路由一旦消失（重启、重插网线），Mac 就会跟两台 Linux 机器一样拿到真实 IP。Linux 的 systemd-resolved 只用第一个 DNS，DHCP 下发的 5.5 实际上基本用不到。

**一个关键事实**：客户端问**外部 DNS**（比如 223.5.5.5）时，包一定要经过默认网关 5.5，旁路由同样能截获。实测 Mac 和 thinklab 问 223.5.5.5，x.com 返回 fake-ip，baidu.com 返回真实 IP。

## 3. DHCP 下发什么 DNS

| | DNS = 192.168.5.5 | **DNS = 223.5.5.5**（选这个） |
|---|---|---|
| 平时分流 | ✅ | ✅（已实测） |
| 旁路由重启那十几秒 | ❌ 全网解析失败 | ⚠️ 查询直接发到阿里，还能上网 |
| 旁路由挂了 | 网关和 DNS 都要改回去 | 只改网关 |
| dae | ❌ 不兼容（官方说不要把 DNS 指向 dae 本机，有环路风险） | ✅ dae 推荐的做法 |
| 风险 | 出问题马上能发现 | 截获失效时会**悄悄**退化成真实 IP |

最终：**所有设备 DNS = 223.5.5.5、119.29.29.29**，**网关按设备区分**。中兴能做到这一点：旁路由自己拿到的网关是 5.1，Mac 拿到的是 5.5。

## 4. 端口、IPv6、防火墙（mihomo 阶段的结论）

- **端口**：ShellCrash 有两条劫持路径。fake-ip 网段 198.18.0.0/15 是**全端口**接管；真实 IP 只接管 22/80/443/8080/8443。DNS 走对了的话，端口列表影响不大。不建议开全部端口，否则 BT、P2P、游戏流量都会去走机场节点。换 dae 以后这个问题就没了：dae 是全端口接管，不需要代理的设备直接放到网关 5.1。
- **IPv6**：整个局域网不用。现状是旁路由和 Mac 都没有公网 IPv6。主路由要关掉 RA/DHCPv6；dae 里对 AAAA 查询一律返回空。
- **防火墙**：iptables → nftables 的改造暂缓。换 dae 之后也就不需要了。
- **`send_redirects`**：旁路由上 `all` 和 `enp1s0` 两个开关都是 1，要**都关掉**（内核按两者的 OR 判断）。dae 的 `auto_config_kernel_parameter: true` 会自动设置。

## 5. 为什么最后选 dae

当初比较三个方案（[[#附：三方案比较]]）时，我以为 dae 做不到"新加坡优先"和"链式第一跳自动切换"。读了 v2.1.1 自带的 `example.dae` 后，发现两点都能做到：

- **新加坡优先**：`filter: name(regex: '^hk_') [add_latency: 300ms]`，给香港加延迟惩罚（香港实测约 43ms，新加坡约 80ms）。
- **AI 链式代理**：链式节点只能写具体节点，所以 6 个中转节点（新加坡 3 个、香港 3 个）各生成一条链，放进 `ai` 组里自动选。

> [!caution] 链式代理的方向跟直觉相反
> dae 的写法是 `'出口 -> 中转'`，即 `'vmess://硅谷 -> trojan://新加坡01'`，**dae 先连右边**。来源：dae discussion #236。

dae 的好处：全端口、eBPF 在内核里直接转发直连流量、改规则只要 `reload` 不断连接、DNS 返回真实 IP。
代价：没有面板；域名分流靠截获 DNS，设备上开了 DoH/DoT 就会失效。

## 11. 经验

- 排查网络问题**先实测再下结论**：我前两次推断都错了，抓计数器、traceroute、`netstat -rnal` 才找到真因。
- macOS 的克隆路由默认看不到，要加 `-a`；ICMP 重定向默认被丢弃，路由错了也不会被纠正。
- 旁路由要关 `send_redirects`，而且 `all` 和网卡两个开关都要关。
- 客户端用外部 DNS + 网关指向旁路由，比 DNS 直接指向旁路由更稳，也兼容 dae。
- dae 链式代理写法是 `出口 -> 中转`，跟直觉相反。
- 别短时间内用各种 target/UA 狂拉订阅，容易被机场限流。

## 附录：config.dae（没有密钥，可以入库）

```
# =====================================================================
#  dae 配置 · 旁路由 192.168.5.5 (NanoPi R4S, enp1s0) · dae v2.1.1 · 由 Alma 维护
#  部署位置：/etc/dae/config.dae  (权限 600)
#
#  网络拓扑：
#    主路由 192.168.5.1 DHCP 给所有设备下发 DNS = 223.5.5.5（以及 119.29.29.29）
#    需要代理的设备：网关 = 192.168.5.5  → 经过 dae
#    不需要代理的设备：网关 = 192.168.5.1 → 完全不经过旁路由
#  dae 不监听 53 端口：客户端发往 223.5.5.5 的 DNS 因为要经过网关，被 dae 在网卡上截获。
#  官方文档原话："Do not point other LAN devices at dae:53 (loop risk)"
#
#  分流策略：
#    局域网 / Tailscale / 自定义直连 → direct
#    AI 服务      → ai    : 硅谷 vmess，经 新加坡(优先)/香港(兜底) 中转
#    国内域名/IP  → direct
#    其余         → proxy : 新加坡优先，新加坡全挂才用香港
#
#  节点在 config.d/nodes.dae，由 /etc/dae/dae-sub-update.py 从机场 Clash 订阅生成。
# =====================================================================

include {
    config.d/*.dae
}

global {
    ##### 基础
    tproxy_port: 12345
    tproxy_port_protect: true
    so_mark_from_dae: 0
    log_level: info

    ##### 网卡
    # 只绑 LAN：只接管"把网关设成 5.5"的设备流量。
    # 不绑 WAN：旁路由自己的流量（SSH、apt、拉订阅）不经过 dae，出问题也能登上来。
    lan_interface: enp1s0
    # 自动设置 ip_forward=1、send_redirects=0（all 和 enp1s0 都关）。
    # 不关 send_redirects 的话，内核会给客户端发 ICMP 重定向，引导它们绕过旁路由直连主路由。
    auto_config_kernel_parameter: true

    ##### 节点健康检查
    tcp_check_url: 'http://cp.cloudflare.com,1.1.1.1'
    tcp_check_http_method: HEAD
    udp_check_dns: 'dns.google:53,8.8.8.8'
    check_interval: 30s
    # 延迟差小于 50ms 不切换，避免来回抖动
    check_tolerance: 50ms

    ##### 连接方式
    # domain：把嗅探到的域名交给代理服务器去解析，避免 DNS 污染，拿到离节点最近的 CDN
    dial_mode: domain
    sniffing_timeout: 100ms
    # 机场节点 sni=baidu.com 且要求跳过证书校验（与原 Clash 配置一致）
    allow_insecure: true
    tls_implementation: tls
}

# ---------------------------------------------------------------- DNS
# 客户端问 223.5.5.5，dae 截获后按下面的规则转发。
dns {
    upstream {
        alidns: 'udp://223.5.5.5:53'
        googledns: 'tcp+udp://8.8.8.8:53'
    }
    routing {
        request {
            # 局域网不用 IPv6：AAAA 一律返回空，客户端只走 IPv4
            qtype(aaaa) -> reject
            # 官方示例：屏蔽 HTTPS 记录，避免 ECH 让域名嗅探失效
            qtype(https) -> reject
            qname(geosite:cn) -> alidns
            fallback: googledns
        }
        response {
            upstream(googledns) -> accept
            # 境外域名却拿到内网 IP，基本是被污染了，换 googledns 重查
            ip(geoip:private) && !qname(geosite:cn) -> googledns
            fallback: accept
        }
    }
}

# ---------------------------------------------------------------- 节点组
group {
    # 普通代理：新加坡优先，香港兜底。
    # 香港延迟加 300ms（实测香港 ~43ms、新加坡 ~80ms），正常情况一定选新加坡；
    # 新加坡全部检测失败时才会落到香港。
    proxy {
        filter: name(regex: '^sg_')
        filter: name(regex: '^hk_') [add_latency: 300ms]
        policy: min_moving_avg
    }

    # AI：硅谷服务器出口，第一跳同样新加坡优先、香港兜底。
    # 健康检查测的是整条链路（中转 + 硅谷），硅谷挂了整组都会失败。
    ai {
        filter: name(regex: '^ai_sg_')
        filter: name(regex: '^ai_hk_') [add_latency: 300ms]
        policy: min_moving_avg
    }

    # 备用：机场美国节点。硅谷服务器长时间不可用时，
    # 把下面 routing 里 AI 规则的 "-> ai" 改成 "-> us"，再 `systemctl reload dae`。
    us {
        filter: name(regex: '^us_')
        policy: min_moving_avg
    }
}

# ---------------------------------------------------------------- 分流规则（从上往下匹配）
routing {
    ### 基础
    dip(224.0.0.0/3, 'ff00::/8') -> direct
    dip(geoip:private) -> direct
    # Tailscale (CGNAT 网段)
    dip(100.64.0.0/10) -> direct
```
