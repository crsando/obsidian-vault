# 核心结论

大模型本身**不会"上网"**。所谓"联网搜索"不是模型内部能力，而是外面套了一层**工具调用（Tool Calling / Function Calling）**机制：

- 模型被训练/提示成：当判断"这个问题训练数据里没有、需要实时信息"时，**不直接回答**，而是吐出结构化的**工具调用指令**（JSON）。
- 由**应用层**去执行搜索，再把结果喂回模型。
- 模型基于结果生成**带引用**的回答。

一句话：**联网搜索 = 工具调用 + 搜索引擎 API + RAG 回填**。难点不在"会搜"，而在工程化——搜索质量、去重、引用溯源、多轮反思循环、成本控制。

---

# 核心五步流程（所有产品的底层都一样）

1. **模型判断**：收到问题，判断训练知识不足、需要实时信息。
2. **输出 Tool Call**：吐出结构化 JSON（搜什么、几个查询词）。
3. **应用层执行**：调**搜索引擎 API**（Bing / Google / Tavily / DuckDuckGo…）。
4. **结果回填**：标题 + 摘要 + URL 塞回上下文（复杂场景还要抓正文）。
5. **带引用生成**：模型基于结果作答，标注引用来源。

# 两条主流实现路线

## 路线 A：官方内置 Web Search 工具（闭源大厂）

OpenAI / Google / Claude 在 API 里内置 `web_search` 工具，背后接 **Bing / Google 搜索 + 自家爬虫**，用户看不到搜索引擎这层。

OpenAI 分**三档**（典型分层）：

| 档位 | 机制 | 特点 |
| --- | --- | --- |
| 普通搜索 | 不推理，模型直接转搜索词丢出去 | 最快，适合快速查询 |
| **Agentic Search** | 推理模型把搜索放进思维链，搜一次→看结果→决定是否换词再搜 | 适合复杂问题，更慢 |
| **Deep Research** | 跑几分钟、上百来源 | 长报告，后台异步跑 |

关键控制参数：

- `search_context_size`：给模型看多少搜索结果（low / medium / high）。
- `filters`：限定 / 屏蔽域名（`allowed_domains` / `blocked_domains`）。
- `sources`：完整来源列表（比内联引用更多）。
- `citation annotations`：内联引用标注（`url_citation`）。
- `search_content_types`：可返回图片结果。
- `external_web_access`：是否只走缓存/索引（离线模式）。

## 路线 B：自己搭 RAG 搜索增强（开源 / 国内主流）

这是 **DeepSeek、Qwen 等开源模型**真正用的路子——因为 **DeepSeek 官方 API 不提供联网搜索**，只有网页版 / App 有"联网"开关。

标准搭法：

**搜索 API（Tavily / SearxNG / Brave / DuckDuckGo / Bing）→ 抓取正文 → 切块 → 检索 → 拼进 prompt**

社区玩 DeepSeek R1 联网基本都是这么搭的（例如 Open WebUI 里选 DuckDuckGo / Brave 作为搜索后端）。

# 深度调研（Deep Research）的多 Agent 架构

不是"多搜几次"这么简单，而是分角色的流水线：

- **Planner（规划者）**：把大问题拆成若干子问题 / 研究问题。
- **Crawler 群（执行者）**：多个爬虫 Agent 并行搜每个子问题。
- **摘要 + 溯源**：每个来源做摘要，保留来源追踪。
- **Publisher（汇总者）**：过滤去重、汇总成带引用的报告。

开源代表：

- **GPT Researcher**：planner + execution + publisher 三件套，受 **STORM** 论文启发；并行化 agent 工作，支持本地文档 + web，可聚合 20+ 来源。
- **browser-use**：让 LLM 像人一样操控真实浏览器（打开页面、点击、填写、翻页），用于需要登录或 JS 渲染的抓取场景。

Perplexity 本质上也是"**搜索 + RAG + 引用**"的答案引擎，只是做了极致的工程化和产品化。
